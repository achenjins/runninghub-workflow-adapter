## 调用与提示词

- 简单请求直接 `run_workflow`，不再强制前置 `rh_context`；唯一匹配工作流跳过内部选流模型，多个候选才规划。已有工作流名也直接校验运行。
- `output_type` 和 `use_reference` 约束成品类型与素材需求；明确要编辑时不会选择没有媒体输入的工作流。多份素材仍需按用途选择，自动绑定只用于唯一当前/引用素材与唯一空槽。
- 已经看过且用途明确的图片不强制再次 inspect；缺项/绑定错误直接带回修正所需的数据。
- 模型可见 JSON 使用紧凑分隔符；候选只返回素材 ID、类型、来源、描述及必要的结果任务 ID。工作流卡片去掉空描述、空枚举、未设置的边界和无关默认角色，保留输入 key、必填性与参数约束。
- 四个 Tool 的说明和参数说明文字合计从 **934 字符减少到 492 字符（约 47.3%）**。这是读取源码后的静态字符统计，包含新增参数说明；不是实际 token、总 schema 大小或线上费用统计。
- 收尾通知使用当前聊天语气的一句短话，不输出任务编号、接口或费用，不臆测成品内容。显式状态命令仍可查看任务 ID，详细阶段错误仍保存在任务记录。

## 边界与待部署确认

通知采用“每个事件至多主动触发一次”的策略。若标记落盘后、通知真正发出前进程退出，或 RPC 响应丢失，可能少一条文字通知；不自动重发以免重复。媒体投递仍保留独立的发送状态和人工补发入口。Maisaka 是否最终回复、回复几条还取决于宿主 Planner 行为，不能据此声称跨系统严格恰好一次。

宿主缺少每轮触发消息 ID／用户 ID 的群聊环境仍使用已有的最近发言人回退。此轮把已解析身份和锚点固定到工具调用内，并校验快照所有权；若不同用户在多个工具调用之间交错发言，宿主未提供的精确归属无法仅靠插件恢复，可能需要重新获取上下文或使用命令。这不是已解决的宿主能力问题。

去重依赖保留的任务日志和触发消息 ID。清空日志、极旧记录被裁剪，或宿主将同一条平台消息赋予新的消息 ID，不在该保证范围内。已经存在的旧记录仍使用原指纹兼容，不能追溯补出缺失的触发消息 ID。

部署后优先人工确认：[测试部署指南](TESTING.md) 中的简单调用、同轮重复调用、取消与完成并发、取消被拒、群号缺失和结果通知场景。本轮没有运行这些场景。

主动通知语义依据：[MaiBot API 参考](https://docs.mai-mai.org/plugin/api-reference) 中 `maisaka.proactive.trigger` 的上下文写入与 Planner 唤醒说明；工具停止标志依据：[工具组件文档](https://docs.mai-mai.org/plugin/tools)。

## 2026-09-10 离线复测修复

配置测试发现一处真实迁移问题：SDK 在模型校验之前补入 `feature` 默认值，原有校验器再用 `setdefault` 合并旧 `detect`、`llm`、`cleanup` 时，用户设置已无法覆盖这些默认值。例如旧配置的 `use_llm=false`、`model=planner`、`recall_seconds=0` 会变成默认值。

将旧分组合并提到 `normalize_plugin_config` 调用 SDK 之前，并与配置模型直接校验共用同一迁移函数。旧开关、模型和零值现均保留；用户显式保存的新 `feature` 值仍优先。测试通过临时目录中的真实 TOML 保存、重新读取和多轮归一化验证，不接触用户配置。

同时更新早期用例中的旧假设：收集必填素材的测试明确开启 `required`；同一消息重复调用应复用任务；压缩后的公共素材数据仅暴露候选 ID；默认视觉摘要失败才返回原图；唯一工作流不调用选流模型。新增用例分别验证新节点非必填时沿用远端提示词、默认视觉模型实际接收图片、摘要缓存和绑定错误自带修正候选，未通过放宽关键断言掩盖失败。

另有 5 项专项覆盖同一触发消息并发改写请求不重复提交、新消息允许再次生成、开始通知后重启及补发不重复通知、主动通知不可用时只发一次兜底文字、取消响应晚于成功结果，以及取消被拒仍阻止下一次付费提交。通知用例调用插件真实通知入口，仅模拟宿主 RPC。
